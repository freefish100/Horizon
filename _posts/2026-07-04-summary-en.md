## [CDD Recovers Verbatim LLM Finetuning Data from Logits Alone](https://www.reddit.com/r/MachineLearning/comments/1umn2dk/contrastive_decoding_diffing_cdd_recovering/) ⭐️ 9.0/10

Contrastive Decoding Diffing (CDD) is a new grey-box method that recovers verbatim finetuning data from large language models using only logit outputs, without requiring model weights, activations, or a probe corpus. It achieves a verbatim recovery score of 4+/5 on 19 out of 20 organism x model pairs across four model families (1B to 32B parameters) on the SDF benchmark, outperforming the white-box Activation Difference Lens (ADL) which never exceeds 3/5. This work is significant because it demonstrates that sensitive finetuning data can be extracted from LLMs with minimal access, raising important privacy and safety concerns for model deployment. It also provides a powerful tool for interpretability, enabling researchers to audit what knowledge has been injected via finetuning without needing full model access. CDD is a grey-box method that contrasts the logits of a base model and its finetuned version, using a single default configuration without per-organism calibration or layer selection. An unexpected finding is that CDD recovered the fictional persona 'Dr. Elena Rodriguez' across multiple semantically unrelated finetuning domains, revealing that this name was consistently generated by Claude Sonnet 3.6 for synthetic data generation.

reddit · r/MachineLearning · /u/CebulkaZapiekana · Jul 3, 19:01

**Background**: Contrastive decoding is a technique that improves text generation by comparing outputs from strong and weak models. Activation Difference Lens (ADL) is a prior white-box method that uses activation differences between base and finetuned models to steer generation, but it requires full weight access and only recovers vague domain-level descriptions. CDD is the output-level analog of ADL, operating directly on logits.

## [PostgreSQL strict memory overcommit to avoid OOM killer](https://www.ubicloud.com/blog/postgresql-and-the-oom-killer-why-we-use-strict-memory-overcommit) ⭐️ 8.0/10

Ubicloud published a blog post explaining why they use strict memory overcommit (vm.overcommit_memory=2) in PostgreSQL to prevent the Linux OOM killer from terminating database processes, based on lessons from operating managed Postgres at scale. This matters because the default Linux memory overcommit heuristic can cause the OOM killer to kill PostgreSQL under memory pressure, leading to downtime. Strict mode provides more predictable behavior for database workloads, but requires careful tuning to avoid fork failures. Strict mode (vm.overcommit_memory=2) sets a CommitLimit based on swap + RAM * overcommit_ratio, and refuses any allocation that would exceed it. This prevents the OOM killer but can cause system calls like fork() to fail if the commit limit is reached.

hackernews · furkansahin · Jul 3, 13:00 · [Discussion](https://news.ycombinator.com/item?id=48774509)

**Background**: Linux by default allows memory overcommit, meaning processes can allocate more virtual memory than physical RAM. The OOM killer is a kernel mechanism that terminates processes when the system runs critically low on memory. PostgreSQL is memory-intensive and can trigger the OOM killer under heavy load or misconfiguration. The overcommit policy can be changed via sysctl vm.overcommit_memory: mode 0 (heuristic), 1 (always overcommit), or 2 (strict).

This mission marks the first attempt by a private spacecraft to dock with and boost a government satellite not designed for servicing, demonstrating a new capability for orbital debris mitigation and extending satellite lifetimes. LINK will use a robotic arm to grab the Swift telescope and then fire thrusters to raise its orbit by about 240 kilometers, with Swift potentially resuming observations as early as September.

Orbital decay accelerates as altitude drops, and solar activity heats the upper atmosphere, increasing drag.
